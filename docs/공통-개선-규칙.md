## 🔧 개선할 기능

- 야간 자율 개선 러너가 커밋 대신 "검증 완료·커밋 대기" 상태를 작업 로그에 남기도록 러너 프롬프트/스크립트 반영 여부 확인

> 모든 프로젝트의 개선 작업에 공통으로 적용되는 정책. **야간 러너는 코드를 수정하지 않고 개선 아이디어만 제안**하며(매일 다른 아이디어), 구현은 사용자가 아침 브리핑에서 🚀 착수를 눌러 지시한 뒤 주간에 진행한다. 프로젝트별 규칙은 각 프로젝트 메인 문서의 갈래 `<프로젝트>-개선-규칙.md`에 따로 둔다.

## 적용 순서

1. 이 문서(공통 규칙)를 먼저 읽는다.
2. 그 다음 프로젝트 개선 규칙 문서를 읽는다. **프로젝트 규칙이 공통 규칙보다 우선**한다 — 단, 아래 '절대 원칙'은 프로젝트 규칙으로도 풀 수 없다.
3. 프로젝트 메인 문서 상단의 **🧭 프로젝트 목적 (한 문장)** 을 읽는다. 이 문장이 개선 목표다 — 모든 후보는 "이 목적에 어떻게 기여하는가"로 판단하고, 기여를 한 문장으로 말할 수 없으면 SKIP. 금지 구역·검증·근거 원칙은 목적보다 항상 앞선다.
4. 목적이 미설정인 프로젝트는 코드 개선을 보류하고 브리핑에 "목적 문장 작성 필요"를 표시한다.

## 🚀 개선 판단 5단계 (머스크 알고리즘 — 이 순서로, 건너뛰기 금지)

1. **요구사항을 의심하라** — 근거(파일:줄·로그·재현) 없는 요구는 요구사항 자체를 버린다.
2. **삭제하라** — 최고의 개선은 코드를 없애는 것. 아래 '기본 개선사항 1(중복 제거)'이 여기에 해당한다.
3. **단순화하라** — 새 의존성·새 추상화는 단순화가 아니다.
4. **가속하라** — 단순해진 다음에야 성능·비용을 올린다.
5. **자동화하라** — 검증된 수동 절차만, 마지막에.

_전체 운영 모델은 [🚀 멀티 프로젝트 운영 철학](jarvis-운영-철학.md) 참조._

## 기본 개선사항 (매번 이 세 가지를 먼저 점검)

1. **불필요한 중복 기능 제거** — 같은 일을 하는 코드·함수·경로가 두 곳 이상이면 하나로 통합 (동작 보존 확인 필수)
2. **에러 발생 요인 제거** — 미처리 예외, 경계 조건 누락, 실패 시 복구 부재 등 에러를 만드는 구조
3. **좀비 프로세스 생성 요인 개선** — 종료되지 않는 자식 프로세스, 해제 안 되는 타이머·리스너·락·파일핸들

## 절대 원칙 (프로젝트 규칙으로 덮어쓸 수 없음)

- **꼭 필요하지 않으면 하지 않는다.** 과잉 리팩토링·스타일 변경·사소한 정리·추측성 기능 추가는 가치 없음. 확신이 없으면 SKIP.
- **목적에 기여하지 않는 개선은 하지 않는다.** 결과 보고의 `[GOAL]` 줄에 프로젝트 목적 문장과의 연결을 반드시 적는다.
- **근거 없는 개선은 하지 않는다.** 어떤 문제/불편/위험이 실제로 있는지 한 문장으로 서술되지 않으면 SKIP. "더 깔끔해 보여서"는 근거가 아니다.
- **한 번에 1건, 범위 작게** — 수정 파일 5개 이내, 기존 동작 보존.
- **파괴적 작업 금지** — 삭제·마이그레이션·의존성 대량 변경·시크릿/환경 파일 변경 금지.
- **에이전트는 절대 혼자 커밋하지 않는다** — `git commit`은 사용자가 기능을 직접 확인한 뒤 **사용자만** 수행한다. 에이전트(야간 러너 포함)는 수정 → 검증(문법 체크·빌드·가능하면 테스트)까지만 하고, 작업 트리에 변경을 남긴 채 작업 로그에 "검증 완료·커밋 대기"로 기록한다. 사용자가 명시적으로 "커밋해"라고 지시한 경우에만 예외.
- **검증 실패 상태로 남기지 않는다** — 검증에 실패하면 변경을 되돌리거나 실패 원인을 작업 로그에 남긴다.
- **push·서버 재시작·배포·앱 교체 금지** — 야간엔 현재 브랜치의 작업 트리 변경까지만(커밋 포함 금지).
- **사용자 문서·튜닝 값은 사용자의 것** — `jarvis/`·`docs/`의 사용자 문서 내용, 체감 튜닝 수치는 무단 변경 금지.

## 📝 브리핑 문구 규칙 (야간 아이디어 · 벤치마킹 제안 · 도구 추천 공통)

> 사용자가 브리핑을 읽고 10초 안에 "무엇이 문제고, 무엇을 어떻게 바꾸며, 그러면 뭐가 좋아지는지"를 말할 수 있어야 한다. (2026-09-01 사용자 피드백: 문제만 제기하고 해결책이 없거나 읽어도 모르겠는 항목이 있음)

1. **제목은 동작형** — `[대상]을 [어떻게] 바꾸기`, 40자 이내. 결과가 드러나야 한다. ❌ "내리막 코칭 로직", "자동매수 이력 화면 없음" → ✅ "내리막 코칭을 '속도 +0.5' → '속도 유지'로 바꾸기", "토스 계좌 화면에 자동매수 이력 표 추가"
2. **세 문장 고정 구조** — 🔍 문제 / 🛠 해결 / 🎯 효과. 각각 한 문장.
   - 🔍 문제: 지금 무엇이 어떻게 잘못/불편한가. 파일:줄·화면·수치 같은 확인 가능한 위치를 포함한다.
   - 🛠 해결: 무엇을 어디에서 어떻게 바꾸는가. 구체 행동만 쓴다.
   - 🎯 효과: 바꾼 뒤 사용자가 체감하는 변화.
3. **금지 표현** — "~일 수 있다"로 끝나는 추측만 있는 문제 제기 · "검토한다 / 고려한다 / 개선한다 / 방안을 찾는다" 같은 행동이 없는 동사 · 해결 없이 문제만 있는 항목(→ 제안하지 않는다).
4. **자기 점검** — 출력 전에 문제→해결→효과가 한 줄기로 이어지는지 다시 읽는다. 셋 중 하나라도 비개발자가 이해 못 하면 다시 쓴다.
5. 러너가 이 구조(`problem`·`solution`·`effect` 필드)로 내지 않은 항목은 브리핑에 올리지 않는다(night_runner 파싱 단계에서 제외).

## 👁 한눈에 보기 원칙 (문서 · 앱 UI 공통 — 상시 개선 대상)

> 문서와 UI는 "직관적 · 간결 · 필요한 것이 한눈에"를 향해 **끝없이 다듬는다.** 야간 러너는 매일 아이디어 후보를 고를 때 이 관점(`angle: "가독성"`)을 **반드시 한 번 검토**한다 — 위반이 없으면 안 내도 되지만, 검토 없이 건너뛰지 않는다.

1. **3초 규칙** — 제목·요약만 보고 무엇인지 알 수 있어야 한다. 못 알아보면 그 제목이 버그다.
2. **한 화면 원칙** — 문서 상단 한 화면 안에 목적 → 현재 상태 → 다음 행동이 보여야 한다. 핵심이 스크롤 밑에 묻히면 위반.
3. **같은 정보는 한 곳에만** — 중복 표시(예: 같은 표 두 번)는 발견 즉시 제거 대상. 자동 생성 블록이 진실의 원천이다.
4. **상태는 아이콘 + 숫자로** — ✅ 3 · 💡 2 · 🔴 1 처럼 요약이 먼저, 상세는 그 아래나 접기로.
5. **긴 문단은 표·목록으로, 읽히지 않는 섹션은 삭제로** — 개선 판단 5단계의 '삭제하라'가 문서에도 적용된다.
6. **행동 버튼은 항목 옆에** — 읽고 나서 할 일(🚀 착수 등)을 찾으러 다니게 하지 않는다.

**위반 후보 예시**: 브리핑이 오래돼 수백 줄로 자람(오래된 섹션 접기/보관 필요) · 메인 문서 상단에 자동 블록이 여러 개 쌓여 개요가 밀림 · 같은 안내 문구가 섹션마다 반복.
